# Отчёт по ДЗ №4. Метрики

## Стек

- **Приложение:** Node.js 22 и Express, метрики через библиотеку `prom-client` 15.
- **База:** PostgreSQL 16, метрики через `postgres-exporter` v0.20.1.
- **Хранилище метрик:** Victoria Metrics v1.155.0 в режиме single, чарт `vm/victoria-metrics-single` 0.50.0.

## Установка

```bash
helm repo add vm https://victoriametrics.github.io/helm-charts/
helm repo update
./scripts/build-images.sh
kubectl -n lifeboard delete job migrate --ignore-not-found
kubectl apply -k k8s/
kubectl apply -k k8s/logging/
helm upgrade --install vm-single vm/victoria-metrics-single --version 0.50.0 -n monitoring -f k8s/metrics/vm-values.yaml
```

Чарт ставится в namespace `monitoring` рядом с Victoria Logs. В `k8s/metrics/vm-values.yaml` я задал хранение 7 дней, том на 2 ГБ и включил встроенный сбор с интервалом 15 секунд. Отдельный vmagent на одном узле не понадобился: Victoria Metrics сама умеет собирать метрики, поэтому Service `vm-single-victoria-metrics-agent` из примера в условии у меня не создаётся.

## Как собираются метрики

Используется pull-модель. Victoria Metrics через service discovery смотрит поды в кластере и забирает метрики у тех, где есть аннотации:

```yaml
template:
  metadata:
    annotations:
      prometheus.io/scrape: "true"
      prometheus.io/port: "3000"
      prometheus.io/path: /metrics
```

Такие аннотации стоят у `backend` (порт 3000) и `postgres` (порт 9187). Новый под подхватывается сам, поэтому после `kubectl scale` ничего настраивать не нужно. Цели видны на http://localhost:8428/targets после проброса порта.

Эндпоинт `/metrics` доступен без авторизации, но только внутри кластера: nginx проксирует наружу лишь `/api/`. Отдельный порт я заводить не стал, этого хватило.

## Метрики рантайма

Их собирает `collectDefaultMetrics` из `prom-client`: память, CPU, задержка event loop, сборка мусора. Например, `nodejs_eventloop_lag_p99_seconds` и `process_resident_memory_bytes`.

Сверх этого в `backend/src/metrics.js` есть HTTP-метрики, они понадобятся для SLA:

- `http_requests_total{method, route, status}` считает запросы;
- `http_request_duration_seconds{method, route}` хранит гистограмму времени ответа.

В метке `route` лежит шаблон вроде `/api/tasks/:id`. Конкретный id там нельзя: каждый дал бы отдельный временной ряд.

## Бизнес-метрики

| Метрика | Что считает | Запрос |
|---|---|---|
| `lifeboard_spaces_created_total` | Созданные разделы | `sum(increase(lifeboard_spaces_created_total[1h]))` |
| `lifeboard_tasks_created_total{priority}` | Созданные таски по приоритету | `sum by (priority) (increase(lifeboard_tasks_created_total[1h]))` |
| `lifeboard_tasks_completed_total` | Таски, переведённые в `done` | `sum(increase(lifeboard_tasks_completed_total[1h]))` |
| `lifeboard_tasks_deleted_total` | Удалённые таски | `sum(increase(lifeboard_tasks_deleted_total[1h]))` |
| `lifeboard_tasks{status}` | Сколько тасок сейчас в базе по статусам | `max by (status) (lifeboard_tasks)` |

Первые четыре это счётчики, они показывают, что люди пользуются продуктом. Последняя это gauge: она считается запросом в базу в момент сбора. Каждая реплика отдаёт одно и то же значение, поэтому нужен `max`, а `sum` завысил бы результат вдвое. Если база недоступна, gauge просто пропадает, а остальные метрики продолжают собираться. Они как раз нужны во время сбоя.

Удаление раздела каскадом удаляет его таски, этот случай в `lifeboard_tasks_deleted_total` не попадает: счётчик видит только прямое удаление таски.

## Метрики Postgres

`postgres-exporter` добавлен сайдкаром в под базы. Контейнеры пода делят сеть, поэтому он подключается к `localhost:5432`, а логин и пароль берёт из Secret `lifeboard-db`. Примеры: `pg_up`, `pg_stat_database_numbackends`, `pg_database_size_bytes`, `pg_locks_count`.

## Проверка

После прогона `scripts/traffic.sh` собираются три цели со статусом up (два пода бэкенда и `postgres-0`) и сама Victoria Metrics. Значения на подах совпали со значениями в базе метрик: на одном поде `lifeboard_tasks_created_total{priority="high"}` равнялось 12, на другом 7, в Victoria Metrics те же числа.

## На что наткнулся

**Неполная метка `route` у ошибок.** Сначала метка собиралась из `req.route`, и у ответов 4xx получалось `/:id`: к моменту ответа Express уже вышел из роутера. Теперь метка вычисляется из пути, а неизвестные адреса попадают в `unmatched`, поэтому случайный запрос к `/wp-admin` не создаст новый ряд. Тесты теперь это проверяют.

**Счётчики живут вместе с подом.** В одном прогоне вышло 19 тасок вместо 20: запрос попал на старый под во время раскатки, и его счётчик исчез вместе с подом. Поэтому счётчики нужно читать через `rate` и `increase`, простая сумма обманывает.

**Свежие данные видны с задержкой.** Victoria Metrics по умолчанию не показывает последние 30 секунд в запросах, это настройка `-search.latencyOffset`. Сразу после нагрузки цифры кажутся заниженными.
